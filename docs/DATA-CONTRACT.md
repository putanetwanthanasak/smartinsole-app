## 3. รูปแบบแพ็กเก็ต (Packet Format)

ทุกค่าเป็น **little-endian**

### 3.1 Sensor Stream Packet (200 bytes)

รวม 8 samples ต่อ 1 packet → ส่ง 6.25 ครั้ง/วินาที (ได้อัตราสุ่มจริง 50 Hz)

**Header (8 bytes)**

| Offset | ขนาด | ชนิด | ฟิลด์ | คำอธิบาย |
|---|---|---|---|---|
| 0 | 2 | uint16 | `seq` | ลำดับ packet วนกลับที่ 0 เมื่อครบ 65535 ใช้ตรวจจับ packet หาย |
| 2 | 4 | uint32 | `t0_ms` | เวลาของ sample แรกในหน่วย ms นับจาก boot |
| 6 | 1 | uint8 | `count` | จำนวน sample ในแพ็กเก็ตนี้ (ปกติ = 8) |
| 7 | 1 | uint8 | `flags` | bit0 = ข้อมูลอิ่มตัว (saturated), bit1 = อยู่ระหว่าง calibration |

**Sample Block (24 bytes × 8)**

| Offset | ขนาด | ชนิด | ฟิลด์ | หน่วย |
|---|---|---|---|---|
| +0 | 12 | uint16 × 6 | `fsr[0..5]` | ADC raw 0–4095 |
| +12 | 6 | int16 × 3 | `accel[x,y,z]` | 4096 LSB/g |
| +18 | 6 | int16 × 3 | `gyro[x,y,z]` | 32.8 LSB/(°/s) |

ระยะห่างระหว่าง sample = 20 ms คงที่ → เวลาของ sample ที่ `i` คือ `t0_ms + (i × 20)`

**ตำแหน่ง FSR (index ต้องตรงกันทั้งซ้ายและขวา)**

| Index | ตำแหน่ง | ชื่ออังกฤษ |
|---|---|---|
| 0 | นิ้วหัวแม่เท้า | Hallux |
| 1 | เนินปลายเท้าที่ 1 | 1st Metatarsal Head |
| 2 | เนินปลายเท้าที่ 3 | 3rd Metatarsal Head |
| 3 | เนินปลายเท้าที่ 5 | 5th Metatarsal Head |
| 4 | กลางเท้า | Midfoot / Lateral Arch |
| 5 | ส้นเท้า | Heel |

### 3.2 Temperature Packet (12 bytes)

| Offset | ขนาด | ชนิด | ฟิลด์ | หน่วย |
|---|---|---|---|---|
| 0 | 2 | uint16 | `seq` | — |
| 2 | 4 | uint32 | `t_ms` | ms จาก boot |
| 6 | 2 | int16 | `temp_forefoot` | 0.01 °C (เช่น 3180 = 31.80°C) |
| 8 | 2 | int16 | `temp_heel` | 0.01 °C |
| 10 | 1 | uint8 | `quality` | 0 = ปกติ, 1 = สัมผัสไม่ดี, 2 = เซนเซอร์ผิดพลาด |
| 11 | 1 | uint8 | `reserved` | สำรองไว้ = 0 |

> ค่า `-32768` หมายถึงอ่านค่าไม่ได้ แอปต้องแสดงเป็น "ไม่มีข้อมูล" ไม่ใช่ตัวเลข

### 3.3 Device Status Packet (8 bytes)

| Offset | ขนาด | ชนิด | ฟิลด์ | คำอธิบาย |
|---|---|---|---|---|
| 0 | 1 | uint8 | `battery_pct` | 0–100 |
| 1 | 2 | uint16 | `battery_mv` | แรงดันจริง (mV) |
| 3 | 1 | uint8 | `foot_side` | 0 = ซ้าย, 1 = ขวา |
| 4 | 1 | uint8 | `fw_major` | เวอร์ชัน firmware |
| 5 | 1 | uint8 | `fw_minor` | — |
| 6 | 1 | uint8 | `state` | 0 = idle, 1 = streaming, 2 = error |
| 7 | 1 | uint8 | `error_code` | 0 = ไม่มี, ดูภาคผนวก A |

### 3.4 Control Commands (App → Insole)

| Opcode | ชื่อ | Payload | คำอธิบาย |
|---|---|---|---|
| `0x01` | START_STREAM | — | เริ่มส่งข้อมูล |
| `0x02` | STOP_STREAM | — | หยุดส่ง (เข้าโหมดประหยัดไฟ) |
| `0x03` | SYNC_TIME | uint64 (unix ms) | ตั้งเวลาอ้างอิงจากมือถือ |
| `0x04` | SET_RATE | uint8 (Hz) | เปลี่ยนอัตราสุ่ม (สำหรับทดสอบ) |
| `0x05` | TARE | — | ปรับ zero-point ของ FSR |
| `0x06` | REBOOT | — | รีสตาร์ต |

## 4. การซิงโครไนซ์เวลาระหว่างเท้าสองข้าง

**ปัญหา:** ESP32 สองตัวมีนาฬิกาแยกกัน ค่า `t_ms` ของแต่ละข้างเริ่มนับคนละจุด หากนำมาเทียบตรงๆ การคำนวณ symmetry และ CoP จะผิด

**วิธีแก้:**

1. เมื่อแอปเชื่อมต่อสำเร็จ ให้ส่ง `SYNC_TIME` พร้อม unix timestamp ปัจจุบันไปทั้งสองข้าง
2. แอปบันทึก `offset = unix_time_ณ_ขณะส่ง − t_ms_ล่าสุดที่ได้รับ` แยกของแต่ละข้าง
3. ทุก sample แปลงเป็น unix time ด้วย `t_unix = t_ms + offset`
4. ทำซ้ำทุก 5 นาที เพื่อชดเชย clock drift

**เกณฑ์ยอมรับ:** ความคลาดเคลื่อนระหว่างสองข้างต้องไม่เกิน **±10 ms** (ครึ่งหนึ่งของช่วง sample)

## 5. การแปลงหน่วย (Calibration)

### 5.1 FSR: ADC → kPa

**ข้อตกลง: ESP32 ส่ง raw ADC — แอปเป็นผู้คำนวณ — แต่ตาราง calibration เก็บไว้ในตัวแผ่นรองเท้า**

| องค์ประกอบ | อยู่ที่ไหน | เหตุผล |
|---|---|---|
| ข้อมูล ADC ดิบ | ส่งผ่าน BLE | เป็น source of truth เก็บไว้ re-calibrate ย้อนหลังได้ |
| ตาราง calibration | NVS ของ ESP32 | แผ่นรองเท้าพก identity ของตัวเองไปด้วย ใช้กับมือถือเครื่องใดก็ได้ |
| สูตรคำนวณ | โค้ดแอป | แก้ไขสูตรได้โดยไม่ต้อง flash firmware ใหม่ |

การออกแบบนี้แก้ปัญหาสำคัญ — หากผู้ป่วยมีแผ่นรองเท้าหลายคู่ หรือเปลี่ยนคู่ใหม่ แอปจะอ่านค่า calibration ที่ถูกต้องได้เองอัตโนมัติจาก characteristic `...b45905` ตอนเชื่อมต่อ ไม่ต้องให้ผู้ใช้ตั้งค่าเอง

> **หมายเหตุการ merge v1.4:** สูตรด้านล่างเป็นเวอร์ชันที่แก้ไขแล้วในรีโปนี้ (offset_adc
> subtraction + หาร 1000 แปลง Pa→kPa — ดู `docs/reports/006-*.md` และ
> `docs/reports/008-*.md`) ไม่ใช่ต้นฉบับจากเจ้าของสัญญา ซึ่งยังไม่มีการแก้ไขนี้ใน
> `DATA-CONTRACT-v1.4-new.md` ที่ได้รับมา (เหมือนกับสถานะตอน merge v1.2)

```
adc_corrected = max(0, adc − offset_adc)   // offset_adc = ค่า ADC ที่จุดศูนย์ (ไม่มีแรงกด) — ผลลัพธ์ของ TARE (opcode 0x05)
V_out = (adc_corrected / 4095) × 3.3
R_fsr = R_pulldown × (3.3 − V_out) / V_out
F_newton = a × R_fsr^b        // a, b จาก curve fitting รายชิ้น
P_kPa = F_newton / A_sensor / 1000   // A_sensor = พื้นที่รับแรงจริง (m²); F_newton / A_sensor คือหน่วย Pa — ต้องหาร 1000 เพื่อแปลงเป็น kPa
```

ค่าที่ต่ำกว่าจุดศูนย์ (adc < offset_adc) หมายถึง drift หรือ noise ของเซนเซอร์ ไม่ใช่แรงกดติดลบ — จึง clamp ที่ 0 เสมอ

ทีมฮาร์ดแวร์ต้องส่งมอบ **ตาราง calibration** ในรูปแบบ JSON:

```json
{
  "device_id": "INSOLE-L-001",
  "r_pulldown_ohm": 10000,
  "sensor_area_m2": 0.000113,
  "channels": [
    { "index": 0, "a": 1.23e5, "b": -1.05, "offset_adc": 12 }
  ]
}
```

## 7. Interface ของโมเดลปัญญาประดิษฐ์

ระบบใช้โมเดล **2 ตัวทำงานต่อเนื่องกัน** ที่คนละระดับเวลา (Multi-Timescale) เพื่อแก้ปัญหาที่อัตราสุ่มของข้อมูลกลไก (50 Hz) กับอุณหภูมิ (1/30 Hz) ต่างกันประมาณ 1,500 เท่า จนไม่สามารถรวมไว้ในหน้าต่างเวลาเดียวกันได้

| | **Model A** — Gait Classifier | **Model B** — Risk Fusion |
|---|---|---|
| หน้าที่ | จำแนกรูปแบบการเดิน | ประเมินระดับความเสี่ยงรวม |
| สถาปัตยกรรม | CNN-LSTM (Single-Branch) | Dual-Branch Intermediate Fusion |
| Input | 24 channels จาก FSR + IMU | Embedding จาก A + อุณหภูมิ + ตัวชี้วัดสมมาตร |
| Window | 2 วินาที | 5 นาที |
| ความถี่ทำนาย | 1 Hz | ทุก 5 นาที |
| Output | Gait class (5 คลาส) | Status Level 1–5 |

> Model B คือส่วนที่ทำให้โครงงานนี้มี **Sensor Fusion แบบกิ่งคู่** ตามที่ระบุไว้ในตารางเปรียบเทียบกับงานวิจัยอื่น กิ่งหนึ่งรับข้อมูลกลไกความถี่สูง อีกกิ่งรับข้อมูลอุณหภูมิความถี่ต่ำ แล้วรวมกันที่ชั้นกลางก่อนตัดสินใจ

| Shape | `[1, 5]` (softmax) — ชื่อ output: `gait_probs` |
| Shape | `[1, 32]` (embedding) — ชื่อ output: `gait_embedding` |
| การตีความ | `argmax` = คลาส, `max` = confidence |

| Index | คลาส | คำอธิบาย |
|---|---|---|
| 0 | `normal` | เดินตามธรรมชาติ |
| 1 | `antalgic` | เดินกะเผลก ลงน้ำหนักข้างหนึ่งสั้นลง |
| 2 | `toe_walking` | เดินเขย่งปลายเท้า ส้นเท้าแตะพื้นน้อยหรือไม่แตะ |
| 3 | `heel_walking` | เดินลงส้นหนัก ปลายเท้าแตะพื้นน้อย |
| 4 | `rotated_foot` | เดินบิดปลายเท้าเข้าใน (in-toeing) หรือออกนอก (out-toeing) |

> **เปลี่ยนจากเวอร์ชัน 1.1:** คลาสเดิม (`minor_asymmetry`, `high_pressure`, `abnormal_gait`, `critical`) เป็นระดับความเสี่ยง ซึ่งไม่สามารถใช้เป็นป้ายกำกับ (label) ในการเก็บข้อมูลกับอาสาสมัครสุขภาพดีได้ เพราะไม่มีทางสั่งให้คนเดิน "แบบ critical" — ระดับความเสี่ยงเป็น**ผลลัพธ์ของการประเมิน** ไม่ใช่ท่าทางที่จำลองได้ คลาสใหม่จึงเปลี่ยนเป็น**รูปแบบการเดิน**ที่อาสาสมัครทำตามคำสั่งได้จริงตามโปรโตคอลการทดสอบ (ดู `SmartInsole_TestProtocol_v1.md`)
>
> **Output shape ไม่เปลี่ยน** — ยังเป็น 5 คลาสเท่าเดิม เปลี่ยนเฉพาะความหมายของแต่ละ index
>
> **โมเดลไม่ได้ตัดสินความเสี่ยงโดยตรง** — `gaitClass` กับ `statusLevel` ใน `RiskAssessment` (ข้อ 6) เป็นคนละค่ากัน `statusLevel` มาจากกฎเกณฑ์ทางคลินิกที่คำนวณจากตัวชี้วัด (PTI, peak, PAI, load concentration — ข้อ 8) ไม่ใช่จาก `argmax` ของโมเดลนี้ ความสัมพันธ์ระหว่างรูปแบบการเดินกับความเสี่ยงเป็นสิ่งที่ต้องพิสูจน์ด้วยข้อมูลจากการทดลอง ไม่ใช่ข้อสมมติที่ฝังไว้ในโมเดล

> โมเดลต้องส่งออก **สอง output** — ทั้ง probability และ embedding ขนาด 32 มิติจากชั้นก่อน softmax เพราะ Model B ใช้ embedding เป็น input ไม่ใช่ใช้ผลคลาสสุดท้าย (embedding เก็บข้อมูลได้ละเอียดกว่ามาก)

## 8. เกณฑ์การแจ้งเตือน (Alert Rules)

### 8.0 พื้นหลังทางคลินิก: กลไกการเกิดแผลกดทับในผู้ป่วยเบาหวาน

หัวข้อนี้อธิบาย**เหตุผลทางคลินิก**ว่าทำไมระบบต้องเฝ้าระวังแรงกดและอุณหภูมิ ไม่ใช่แค่ข้อกำหนดทางเทคนิค — ใช้เป็นพื้นฐานอ้างอิงสำหรับเกณฑ์ทุกข้อในหัวข้อ 8

**กลไกเกิดแผลมี 3 ขั้นตอนที่ต่อเนื่องกัน (International Working Group on the Diabetic Foot, 2023):**

1. **เส้นประสาทรับความรู้สึกเสื่อม (sensory neuropathy) → สูญเสียการรับความรู้สึกป้องกันตัว (Loss of Protective Sensation, LOPS)**
   ผู้ป่วยรับรู้แรงกด ความเจ็บ และอุณหภูมิได้น้อยลงหรือไม่รู้สึกเลย ทำให้บาดเจ็บเล็กน้อยจากแรงกดซ้ำๆ ไม่ถูกตรวจพบและลุกลามกลายเป็นแผล — นี่คือจุดเชื่อมโยงหลักระหว่างเส้นประสาทเสื่อมกับการเกิดแผล

2. **เส้นประสาทสั่งกล้ามเนื้อเสื่อม (motor neuropathy) → โครงสร้างเท้าเปลี่ยนรูป**
   กล้ามเนื้อเล็กภายในเท้าฝ่อลง เกิดความไม่สมดุลระหว่างกล้ามเนื้องอ-เหยียด นำไปสู่นิ้วเท้าโก่งงอ (claw/hammer toe) และหัวกระดูกฝ่าเท้ายื่นเด่นขึ้น ทำให้ตำแหน่งจุดรับน้ำหนักเปลี่ยนไปจากเดิม

3. **แรงกดสะสมที่จุดใหม่ + ไม่รู้สึกเจ็บ → หนังด้าน → แผล**
   ร่างกายตอบสนองต่อแรงกดสูงด้วยการสร้างหนังด้าน (callus) ซึ่งกลับเพิ่มแรงกดที่จุดนั้นมากขึ้นไปอีกเป็นวงจรลูป จนเนื้อเยื่อใต้ผิวสลายตัวกลายเป็นแผล ตำแหน่งที่พบบ่อยที่สุดคือ**ส้นเท้าและหัวกระดูกฝ่าเท้า** (Neuropathic Ulcer, StatPearls)

**ประเด็นสำคัญที่ทำให้ระบบนี้มีความหมาย:** ผู้ป่วยไม่ได้ตั้งใจลงน้ำหนักผิดตำแหน่ง แต่**เพราะรับรู้ไม่ได้ จึงไม่ปรับท่าเดินเพื่อเลี่ยงจุดที่รับแรงเกิน** ต่างจากคนสุขภาพดีที่ร่างกายจะปรับท่าเดินอัตโนมัติทันทีที่รู้สึกเจ็บหรือไม่สบาย ระบบเฝ้าระวังที่ตรวจจับแรงกดสะสมได้จึงทำหน้าที่แทนความรู้สึกที่ผู้ป่วยสูญเสียไป

> **ข้อจำกัดที่ต้องระบุในเล่ม:** อาสาสมัครในโปรโตคอลการทดสอบ (`SmartInsole_TestProtocol_v1.md`) เป็นคนสุขภาพดีที่จำลองท่าเดิน ซึ่งยังคงรับรู้ความรู้สึกและปรับตัวได้ตามปกติตลอดการทดสอบ ข้อมูลที่เก็บได้จึงแสดง**แรงกดที่เกิดจากท่าทางการเดินเพียงอย่างเดียว** ไม่ได้จำลอง**พฤติกรรมของผู้ป่วยที่ไม่รู้สึกตัวและไม่ปรับท่าเดิน** ซึ่งเป็นกลไกที่แท้จริงของการเกิดแผลกดทับในทางคลินิก การนำระบบไปใช้กับผู้ป่วยจริงจึงยังต้องมีการศึกษาต่อเนื่องเพื่อยืนยันประสิทธิภาพ

### 8.1 หลักการ: ใช้ความสมมาตรแทนค่าฐานส่วนบุคคล

ระบบ **ไม่เก็บ baseline ส่วนบุคคล** เนื่องจากข้อจำกัดด้านการเก็บข้อมูลผู้ใช้และเพราะกลุ่มทดสอบของโครงงานเป็นอาสาสมัครสุขภาพดีที่จำลองท่าเดินผิดปกติ ซึ่งไม่มีค่าฐานระยะยาวให้เก็บอยู่แล้ว

แทนที่จะเทียบกับประวัติของผู้ใช้ ระบบใช้ **เท้าอีกข้างของผู้ใช้เองเป็นกลุ่มควบคุม** ซึ่งเป็นหลักการเดียวกับที่เกณฑ์ ΔT 2.2 °C ของ Lavery ใช้อยู่ — งานวิจัยไม่ได้กำหนดว่าอุณหภูมิสัมบูรณ์เท่าใดคืออันตราย แต่กำหนดจากผลต่างระหว่างสองข้างที่วัดพร้อมกัน เพราะวิธีนี้ตัดตัวแปรกวนอย่างอุณหภูมิห้อง น้ำหนักตัว และช่วงเวลาของวันออกไปได้เกือบทั้งหมด

**ข้อดีเพิ่มเติม** — ระบบใช้งานได้ทันทีตั้งแต่นาทีแรกที่สวมใส่ ไม่ต้องรอสะสมข้อมูล และเทียบระหว่างผู้ใช้ต่างคนได้โดยไม่ต้องปรับค่าตามน้ำหนักตัว

### 8.2 ตัวชี้วัดเชิงสมมาตร

| ตัวชี้วัด | สูตร | เกณฑ์ |
|---|---|---|
| Peak Asymmetry Index (PAI) | `abs(L−R) / ((L+R)/2) × 100` | > 15% = เฝ้าระวัง |
| PTI Asymmetry Index | เทียบแรงกดสะสมซ้าย-ขวา | > 20% = เฝ้าระวัง |
| Load Concentration | `จุดที่สูงสุด / ผลรวม 6 จุด × 100` | จุดเดียว > 40% = เสี่ยง |
| Within-Session Drift | เทียบ 5 นาทีแรกกับ 5 นาทีท้าย | เพิ่ม > 25% = ล้า/ชดเชยท่าเดิน |

> **ข้อควรระวัง** — การเทียบซ้าย-ขวาใช้ FSR คนละชุด หากเซนเซอร์สองข้างให้ค่าไม่ตรงกันจะเกิดความไม่สมมาตรปลอม (False Asymmetry) จึงต้องทำ **bench calibration** ตอนประกอบ โดยกดแผ่นรองเท้าทั้งคู่ด้วยน้ำหนักมาตรฐานเดียวกันแล้วบันทึกค่าชดเชยลง NVS (ดูข้อ 5.1) ขั้นตอนนี้ทำครั้งเดียวที่โรงงาน/ห้องแล็บ ไม่ต้องเก็บข้อมูลจากผู้ใช้เลย

#### 8.3.1 ข้อความเสริมตามรูปแบบการเดิน (ไม่ใช่เกณฑ์แจ้งเตือนใหม่)

เมื่อเกณฑ์ข้อใดข้อหนึ่งข้างต้น (`PRESSURE_WATCH`/`PRESSURE_PEAK`/`PRESSURE_PTI`/`LOAD_CONCENTRATION`) ทริกเกอร์ที่โซนใดโซนหนึ่ง **และ** ในช่วงเวลาเดียวกัน Model A ทายรูปแบบการเดินที่สอดคล้องกับโซนนั้นด้วย confidence ≥ `MIN_CONFIDENCE` (0.60) ให้เติมข้อความอธิบายเหตุผลต่อท้ายข้อความแจ้งเตือนเดิม **โดยไม่เปลี่ยนระดับ (`statusLevel`) หรือสร้างเกณฑ์แจ้งเตือนใหม่**

| รูปแบบการเดิน | โซนที่เกี่ยวข้อง | ข้อความเสริม (ไทย) | ที่มา |
|---|---|---|---|

| `toe_walking` | hallux, meta1 | "ตรวจพบรูปแบบเดินเขย่งปลายเท้า ซึ่งอาจเพิ่มแรงกดบริเวณปลายเท้า" | นิ้วหัวแม่เท้าและหัวกระดูกฝ่าเท้าที่ 1 เป็นบริเวณเสี่ยงแผลกดทับหลักตามวรรณกรรม (Ahmad Sharoni et al., 2021); PPP บริเวณปลายเท้าสูงกว่ากลุ่มควบคุมในผู้ป่วยเบาหวานที่มีเส้นประสาทเสื่อม (Mueller et al.) |
| `rotated_foot` (in-toeing) | midfoot, meta5 | "ตรวจพบรูปแบบเดินบิดเท้าเข้า ซึ่งงานวิจัยพบว่าเพิ่มแรงกดด้านนอกเท้าได้ถึง 61% (กลางเท้า) และ 49% (ปลายเท้า)" | Chang et al. — การเดิน in-toeing เพิ่มภาระกลางเท้า/ปลายเท้าฝั่งนอกอย่างมีนัยสำคัญ |
| `rotated_foot` (out-toeing) | midfoot, meta1 | "ตรวจพบรูปแบบเดินบิดเท้าออก ซึ่งงานวิจัยพบว่าเพิ่มแรงกดด้านในเท้าได้ถึง 72% (กลางเท้า) และ 52% (ปลายเท้า)" | Chang et al. — การเดิน out-toeing เพิ่มภาระกลางเท้า/ปลายเท้าฝั่งในอย่างมีนัยสำคัญ |
| `antalgic` | — (ไม่ระบุจุดเจาะจง) | "ตรวจพบรูปแบบเดินไม่สมมาตร ควรตรวจสอบแรงกดทั้งสองข้างเทียบกัน" | ความไม่สมมาตรของการเดินสัมพันธ์กับแรงกดฝ่าเท้าที่เพิ่มขึ้นและความเสี่ยงต่อเนื้อเยื่ออ่อน (งานวิจัยกลุ่มผู้พิการขาส่วนล่าง — ใช้เป็นหลักฐานเชิงกลไก ไม่ใช่ประชากรเดียวกับกลุ่มทดสอบ) |
| `normal` | — | ไม่เติมข้อความ | — |

**ข้อจำกัดที่ต้องระบุในเล่มกำกับตารางนี้เสมอ:**
1. งานวิจัยทั้งหมดข้างต้นวัด**การกระจายตัวของแรงกด** ไม่ใช่**อัตราการเกิดแผลจริง** จากรูปแบบการเดินนั้นๆ โดยตรง — ความเชื่อมโยงกับความเสี่ยงแผลกดทับมาจากการต่อกับความรู้แยกต่างหากว่าบริเวณแรงกดสูง = บริเวณเสี่ยงแผล ไม่ใช่ข้อสรุปที่วัดตรงในงานวิจัยเดียวกัน
2. หลักฐานมีน้ำหนักไม่เท่ากันในแต่ละท่า — `rotated_foot` มีงานที่ให้ผู้เข้าร่วมเดินเลียนแบบท่านั้นโดยตั้งใจแล้ววัดจริง (methodology ใกล้เคียงกับโปรโตคอลของโครงงานนี้ที่สุด) ส่วน `toe_walking`/`heel_walking` เป็นการต่อข้อเท็จจริงสองอย่างเข้าด้วยกัน (ไม่ได้วัดตรง) และ `antalgic` เป็นการอนุมานข้ามกลุ่มประชากร (ผู้พิการขาเทียม ไม่ใช่คนสุขภาพดีที่แกล้งเดินกะเผลก) จึงมีน้ำหนักอ่อนที่สุด ใช้ถ้อยคำ "อาจ" กำกับในสองท่านี้เพื่อสะท้อนความไม่แน่นอนนี้
3. ข้อความเสริมเหล่านี้มีไว้เพื่อ**อธิบายเหตุผล** ประกอบการแจ้งเตือนที่เกิดจากค่าที่วัดได้จริงเท่านั้น ไม่ใช่เกณฑ์ที่ใช้ตัดสินใจแจ้งเตือนเอง — ถ้าไม่มีเกณฑ์อื่นทริกเกอร์ ท่าเดินเพียงอย่างเดียวจะไม่ทำให้เกิดการแจ้งเตือน

**ข้อเสนอแนะงานวิจัยต่อ (บันทึกไว้ ยังไม่ทำในโครงงานนี้):** ความเชื่อมโยงระหว่างรูปแบบการเดินกับตัวชี้วัดความเสี่ยงที่วัดได้จริง (PTI/PAI/load concentration ต่อโซน) สามารถทดสอบได้จากข้อมูลที่เก็บจากอาสาสมัคร 30 คนโดยเปรียบเทียบแบบ paired กับท่า `normal` ของคนเดียวกัน — ยังไม่ได้ทำในเวอร์ชันนี้เพื่อไม่ให้เบี่ยงเบนขอบเขตของโครงงานจากการพัฒนาระบบไปเป็นงานวิจัยเชิงสถิติ

#### 8.3.2 เกณฑ์ตรวจจับการเดิน (Walking Gate) สำหรับ `PRESSURE_PEAK`

> **เพิ่มเติมนอกเอกสารต้นฉบับ (local addition, v1.5) — ยังไม่ส่งกลับให้เจ้าของสัญญา.** ต่างจากหมายเหตุใน §5.1 ซึ่งเป็นการ "แก้ไข" สูตรที่มีอยู่แล้วในเอกสารต้นฉบับให้ถูกต้อง ข้อ 8.3.2 นี้คือ "เพิ่ม" กลไกที่ไม่เคยมีอยู่ใน draft ใดของเจ้าของสัญญาเลย — implement แล้วจริงใน `AlertStore.ts`/`constants.ts` ของแอป (ดู `docs/BACKLOG.md` ข้อ 10 และ `docs/reports/017-*.md`) แต่ยังไม่เคยเสนอกลับให้เจ้าของสัญญารับทราบหรือรับรอง

ตาราง §8.3 กำหนดเงื่อนไข `PRESSURE_PEAK` ว่าต้องเป็น "Peak > 200 kPa **ขณะเดิน**" — ไม่ใช่ขณะนั่งหรือยืนนิ่งที่บังเอิญมีแรงกดสูงที่เท้า เดิมทีไม่มีกลไกใดในแอปตรวจสอบเงื่อนไข "ขณะเดิน" นี้เลย (พบระหว่างตรวจสอบเกณฑ์ทั้งหมดในตาราง §8.3 กับสิ่งที่ implement จริง) ข้อนี้อธิบายกลไกที่ `AlertStore` ใช้อุดช่องโหว่นั้น

**หลักการทำงาน:** ระดับแจ้งเตือนของ `PRESSURE_PEAK` (แรงกด > `alertKpa`) จะยิงแจ้งเตือนได้ก็ต่อเมื่อตรวจพบว่าผู้ใช้กำลังเดินอยู่ ณ ขณะนั้นเท่านั้น หากแรงกดสูงเกิดขึ้นขณะไม่ได้เดิน (เช่น นั่งพักโดยเท้าทับของหนัก) การแจ้งเตือนจะ**ไม่ตกไปเป็น "ไม่แจ้งเตือนเลย"** แต่ยังคงแสดงผลที่ระดับ `PRESSURE_WATCH` (เฝ้าระวัง) แทน เพราะเงื่อนไขของ `PRESSURE_WATCH` ในตาราง §8.3 ไม่มีข้อกำหนดเรื่อง "ขณะเดิน" กำกับไว้ — แรงกดสถิตสูงยังคงมีประโยชน์ที่จะแสดงบน heatmap แม้จะยังไม่ใช่อันตรายเฉียบพลันที่ควร push notification

**วิธีตรวจจับ:** คำนวณค่าเฉลี่ยของส่วนเบี่ยงเบน (mean deviation) ของขนาดเวกเตอร์ความเร่ง (accel magnitude = √(x²+y²+z²), หน่วย g) จาก 1g ในช่วงหน้าต่างเวลา `walkingWindowMs` ล่าสุด แล้วเทียบกับเกณฑ์ `walkingAccelG` — ถือว่า "กำลังเดิน" เมื่อค่าเฉลี่ยนี้ ≥ `walkingAccelG`

ใช้ **ขนาดเวกเตอร์** (ไม่ใช่ค่าจากแกนใดแกนหนึ่งของ IMU โดยตรง) เพราะทิศทางของ IMU ที่ติดอยู่กับเท้าหมุนเปลี่ยนไปตลอดวงจรการเดิน (gait cycle) — ขนาดเวกเตอร์เป็นค่าคงที่ (invariant) ที่ยังคง ≈1g เมื่อเท้านิ่ง ไม่ว่าเท้าจะวางในทิศทางใดขณะนั้น ในขณะที่การเทียบค่าจากแกนใดแกนหนึ่งตรงๆ จะไม่เป็น orientation-invariant — ผลลัพธ์จะแกว่งไปตามมุมที่เท้าวาง ไม่ใช่ตามการเคลื่อนไหวจริง

เพิ่มบล็อก `motion` ในโครงสร้าง `thresholds.json` ของข้อ 8.3:

```json
"motion": { "walkingAccelG": 0.15, "walkingWindowMs": 800 }
```

> **PROVISIONAL — สถานะเดียวกับ `PRESSURE_WATCH_KPA`/`PRESSURE_ALERT_KPA` ข้างต้น (ตกลงกันไว้ ไม่ใช่ตรวจสอบแล้ว).** ค่าทั้งสอง (0.15g, 800ms) เป็นค่าประมาณเบื้องต้น (best-guess) เลือกจากการประมาณช่องว่างระหว่างสัญญาณรบกวนของเซนเซอร์ขณะยืนนิ่งกับความเร่งทั่วไปขณะเดิน — **ยังไม่มีข้อมูลจริงจาก IMU ที่ติดตั้งบนเท้าจริงมายืนยัน** เพราะยังไม่มี PCB ให้ทดสอบ (สถานะเดียวกับข้อ 12 ในภาคผนวก backlog ของแอป) ต้องปรับค่าอีกครั้งเมื่อมีข้อมูลการเดินจริงจากฮาร์ดแวร์

**ข้อตกลงเรื่องเกณฑ์แรงกดสองระดับ**

| ระดับ | ค่า | การแสดงผล | แจ้งเตือน |
|---|---|---|---|
| เฝ้าระวัง | 75 kPa | วงกลมสีส้มบน heatmap | ไม่ push notification |
| แจ้งเตือน | 200 kPa | วงกลมสีแดง + ป้าย ALERT | push notification |

> **หมายเหตุทางเทคนิคที่ต้องระบุในเล่ม** — ค่า 200 kPa จากงานวิจัยได้มาจากแผ่นวัดที่มีเซนเซอร์หลายร้อยจุด ขณะที่ระบบนี้มี FSR เพียง 6 จุดต่อข้าง จึงมีโอกาสวัดไม่ตรงตำแหน่งที่แรงกดสูงสุดจริง ทำให้ค่าที่อ่านได้มีแนวโน้มต่ำกว่าความเป็นจริง ตัวชี้วัดเชิงสมมาตรในข้อ 8.2 จึงถูกออกแบบมาเพื่อชดเชยข้อจำกัดเชิงพื้นที่นี้โดยเฉพาะ

**ค่าเกณฑ์ทั้งหมดต้องเก็บในไฟล์ `thresholds.json` ห้าม hardcode ในโค้ด** เพราะจะต้องปรับหลังการทดสอบกับฮาร์ดแวร์จริงอย่างแน่นอน

```json
{
  "version": 1,
  "pressure": { "watchKpa": 75, "alertKpa": 200, "ptiKpaS": 80 },
  "temperature": { "deltaC": 2.2, "consecutiveReadings": 2 },
  "asymmetry": { "peakPct": 15, "ptiPct": 20, "concentrationPct": 40 },
  "model": { "minConfidence": 0.60 },
  "motion": { "walkingAccelG": 0.15, "walkingWindowMs": 800 }
}
```

> **`motion` เพิ่มใน v1.5 — ดูข้อ 8.3.2.** สี่บล็อกแรก (`pressure`/`temperature`/`asymmetry`/`model`) มาจากเจ้าของสัญญา; `motion` เป็นการเพิ่มเติมนอกเอกสารต้นฉบับ ยังไม่ส่งกลับให้เจ้าของสัญญา — เหมือนสถานะของสูตร §5.1 ที่แก้ไขในรีโปนี้แต่ยังไม่อัปสตรีม

`{ "version": 1, ... }` ในบล็อกนี้คือเลขเวอร์ชันของ**ไฟล์ `thresholds.json` เอง** (schema ของไฟล์ค่าคงที่รันไทม์) แยกจากเลขเวอร์ชันของเอกสารสัญญาฉบับนี้ (v1.5) — สองเลขนี้ไม่ผูกกัน

### 8.4 การรวมผล (Fusion)

```
statusLevel = max(ระดับจากทุกกฎที่เข้าเงื่อนไข, ระดับจาก Model B)
```

ใช้ค่าสูงสุดเพื่อความปลอดภัยของผู้ป่วย (fail-safe) — ยอมเตือนเกินดีกว่าพลาด

> `gaitClass` (ผลของ Model A) **ไม่เข้าสมการนี้โดยตรง** ใช้เฉพาะเป็นข้อความเสริมตามข้อ 8.3.1 เท่านั้น — สอดคล้องกับหลักการในข้อ 7.2 ที่ว่าความสัมพันธ์ระหว่างรูปแบบการเดินกับความเสี่ยงต้องพิสูจน์ด้วยข้อมูล ไม่ใช่ข้อสมมติที่ฝังไว้ในระบบ

### 8.5 การป้องกันการเตือนซ้ำ


- แจ้งเตือนรหัสเดียวกันได้ไม่เกิน 1 ครั้งต่อ **30 นาที**
- ทุกการแจ้งเตือนต้องมีข้อความคำแนะนำภาษาไทยกำกับเสมอ ไม่แสดงเพียงตัวเลข

## 9. Schema ของ Firebase

**หลักการ: ไม่ส่งข้อมูลดิบ 50 Hz ขึ้น cloud** — เก็บใน SQLite และซิงค์เฉพาะข้อมูลสรุปกับเหตุการณ์

```
users/{uid}
  ├─ profile        : { displayName, iwgdfRiskGroup, createdAt }
  ├─ devices/{id}   : { side, lastSeen, firmware, batteryPct }
  ├─ hourly/{yyyyMMddHH}
  │     { steps, walkMinutes, peakKpaL, peakKpaR, ptiL, ptiR,
  │       avgTempForefootL, avgTempForefootR, maxDeltaT,
  │       symmetryScore, dominantGaitClass }
  ├─ alerts/{alertId}
  │     { code, tUnixMs, level, valueSnapshot, adviceTh,
  │       acknowledged, source }
  └─ sessions/{sessionId}
        { startMs, endMs, sampleCount, uploadedAt }
```

**นโยบายการซิงค์**

| ข้อมูล | ความถี่ | เงื่อนไข |
|---|---|---|
| `alerts` | ทันที | เมื่อมีเน็ต ถ้าไม่มีให้ queue ไว้ |
| `hourly` | ทุก 1 ชม. | Wi-Fi หรือ mobile data |
| `devices` | เมื่อสถานะเปลี่ยน | — |
| ข้อมูลดิบ | ไม่ซิงค์ | เก็บใน SQLite เท่านั้น |
